# معيار نشر مقالات بريق — Article Publish Standard

هذا الملف هو المسار المعتمد لإضافة أي مقال جديد بعد وصول المدونة إلى 15 مقالًا. الهدف هو منع تكرار عوائق النشر القديمة وفصل النشر التحريري عن ترقية الصوت عندما تكون بوابات TTS مجمّدة.

## الدرس من الإصدارات السابقة

- PR #3 وPR #4 أثبتا أن المقال ليس ملف Markdown فقط؛ الحزمة الناجحة تشمل النص والصورة/المصغرات وبيانات التحرير وفحوص البناء، وكان الصوت يستخدم مسار fallback عندما يتعذر Gemini.
- PR #17 وPR #24 ثبّتا أن نافذة بريق جزء من عقد النشر وأن Cloudflare Pages Git integration هو مالك النشر والـPreview.
- PR #92 وPR #93 كشفا أن إضافة مقال جديد بعد 15 مقالًا تصطدم ببوابات قديمة ثابتة العدد وباشتراطات Speech Script/Window.
- واجهة المقال تدعم أصلًا حالة عدم توفر الصوت: تبويب «صدى» يكون معطلًا ويعرض «قيد الإعداد». لذلك لا يجب أن يوقف تجميد TTS نشر النص الموثق والنافذة البصرية.
- الصوت المنشور القديم أصل محمي: لا يعاد توليده أو لمسه عند نشر مقال جديد.

## الحزمة الإلزامية لكل مقال جديد

1. `src/content/posts/<slug>.md`
   - Front Matter مطابق للمخطط.
   - `draft:false` فقط عند الجاهزية.
   - مصادر خارجية قابلة للنقر داخل المتن.
   - رابط داخلي سياقي مناسب.
2. صورة رئيسية + thumbnail metadata.
   - يفضّل مصدر 1600×900 وهوية بريق.
   - تمر عبر مسار الصور الحالي عند استخدام WebP.
3. `src/data/visual-stories/<slug>.json`
   - 7–10 بطاقات محررة يدويًا.
   - `sourceFingerprint` مطابق للمقال.
4. `src/data/visual-stories/<slug>.skeleton.json`
   - الهيكل/الأثر التحريري المطلوب للمولد والفحص.
5. `scripts/speech-scripts/<slug>.json`
   - يجب أن يكون متزامنًا مع النص.
   - إذا لم يراجع النطق بعد: `status=needs-linguistic-review` ولا يدّعي اعتمادًا غير موجود.
6. `scripts/speech-test-clips/<slug>.json`
   - حالة pending حتى اكتمال المراجعة الصوتية.
7. الصوت:
   - إن وجد Manifest منشور في `public/audio/articles/<key>/manifest.json` فيجب أن يجتاز جميع فحوصه ويبقى محميًا.
   - إن لم يوجد بسبب تجميد/حصة TTS، ينشر المقال نصيًا ومرئيًا ويظهر «صدى — قيد الإعداد».
   - لا توليد تلقائي ولا توسيع للحد الصوتي دون سياسة/تفويض مستقل.

## بوابات ما قبل الدمج

يجب أن ينجح:
- Bareeq Arabic Quality Gate.
- Visual Story fingerprint/editorial/runtime.
- Typecheck.
- `npm run build` كاملًا.
- Viewport QA لكل القصص الموجودة ديناميكيًا × 4 viewports.
- Cloudflare Pages branch Preview عبر التكامل الأصلي مع GitHub.

لا يدمج PR المقال قبل نجاح build وCloudflare Preview، إلا إذا كان الفشل مثبتًا كعطل بنية عام وتم إصلاحه في PR مستقل ثم إعادة الاختبار.

## النشر الصحيح

1. فرع مقال واحد مبني على أحدث `main`.
2. رفع الحزمة كاملة، لا Markdown منفردًا.
3. فتح PR.
4. معالجة أول فشل حقيقي فقط وعدم تجاوز البوابات.
5. انتظار تعليق Cloudflare Pages bot:
   - Preview ناجح = مؤهل للدمج.
   - Build failed = قراءة السبب وإصلاحه على نفس الفرع.
6. Squash merge إلى `main` مع تثبيت head SHA.
7. التحقق من:
   - صفحة المقال الحية.
   - زيادة عداد القسم.
   - الرئيسية/الأرشيف/sitemap/RSS.
   - الصورة ونافذة بريق.
   - «صدى»: يعمل إذا كان الصوت منشورًا، أو يظهر «قيد الإعداد» إن كان الصوت مؤجلًا.

## ممنوع

- إنشاء قناة نشر موازية لـCloudflare ما دام Git integration الأصلي قائمًا.
- إضافة API tokens للنشر لمجرد تجاوز Preview فاشل.
- إعادة توليد أصوات المقالات القديمة عند نشر مقال جديد.
- جعل عدد المقالات أو القصص ثابتًا مثل 15 داخل بوابات الجودة.
- اعتبار Merge إلى main دليلًا على نجاح النشر؛ الدليل هو الصفحة الحية.

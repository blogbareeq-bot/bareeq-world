# قائمة تدقيق النشر — مقال «لماذا تفتح بعض جوازات السفر أبواب العالم أكثر من غيرها؟»

**المعرف:** `why-some-passports-are-stronger`  
**الحالة الحالية:** جاهز تحريريًا، الصور وطبقة النطق جاهزة، والمقال ما يزال `draft: true` عمدًا حتى يكتمل الصوت الإنتاجي والفحص النهائي.

## قفل المتن النهائي

تم إغلاق آخر ملاحظة تحريرية في تعريف الدخول دون تأشيرة، وأصبح النص يوضح أن الإعفاء من التأشيرة لا يلغي شروط الدخول المعتادة للدولة المستقبلة.

**bodyHash النهائي الحالي:**

`2b2999dba95bff5e6bfb8ff16d2848fa3b677ffe8f595a5b6166ca15ebf7d4c1`

هذا هو SHA-256 لجسم المقال بعد الـfrontmatter، بعد توحيد أسطر CRLF وقص الفراغات. أي تعديل لاحق في المتن يوجب إعادة حسابه قبل توليد الصوت.

## لماذا يبقى draft:true الآن؟

بوابات بريق ترفض أي مقال منشور بلا صوت إنتاجي كامل و`manifest.json` صالح. المقال الجديد لا يملك حتى الآن manifest صوتيًا في:

`public/audio/articles/34e34b6f4633d928/manifest.json`

لذلك لا يُدمج ولا يُنشر قبل تنفيذ خطوات يوم النشر أدناه.

## حزمة يوم النشر

يوجد ملفان متتابعان، ويجب تطبيقهما **بالترتيب**:

1. `docs/editorial/publish-day-why-some-passports-are-stronger.patch`
2. `docs/editorial/publish-day-why-some-passports-final-fixes.patch`

الملف الأول يحول المنظومة إلى 14 مقالًا ويضيف المقال إلى `PENDING_CLOUD` ويقلبه إلى `draft:false` ويضيف Speech Review الأساسي.

الملف الثاني إلزامي بعده مباشرة؛ فهو:

- يحدث `speech-review` إلى الـbodyHash النهائي الحالي.
- يصحح رسالة `check-production-voices-v4200.mjs` من 13 إلى 14 مقالًا.
- يصحح رسائل `check-audio-mobile.mjs` من 11+2 إلى 12+2.

لا تشغّل أي بوابة إصدار بين تطبيق الملفين.

## الترتيب الصحيح يوم النشر — مهم جدًا

### 1. طبق حزمة النشر الأساسية

```bash
git apply docs/editorial/publish-day-why-some-passports-are-stronger.patch
```

### 2. طبق الإصلاحات النهائية للحزمة فورًا

```bash
git apply docs/editorial/publish-day-why-some-passports-final-fixes.patch
```

### 3. حدّث وقت النشر

عدّل `publishedAt` في المقال إلى وقت النشر الحقيقي. تغيير الـfrontmatter لا يغير `bodyHash`.

### 4. ولّد صوت المقال الجديد مباشرة قبل Full Build

لا تبدأ بـ`npm run build` فورًا بعد تطبيق الحزمة.

السبب: `run-v4211-audio.mjs` يفحص اكتمال baseline لجميع المقالات قبل خطوة Gemini التقدمية، والمقال الجديد لا يملك fallback صوتيًا سابقًا. لذلك يجب إنشاء صوت المقال الجديد المستهدف أولًا.

مع وجود `GEMINI_API_KEY` الإنتاجي في البيئة شغّل:

```bash
BAREEQ_TTS_PROVIDER=gemini \
BAREEQ_TTS_INCLUDE_IDS=why-some-passports-are-stronger \
BAREEQ_TTS_MAX_MISSING_ARTICLES_PER_BUILD=1 \
node scripts/generate-audio.mjs
```

هذا الاستدعاء مستهدف للمقال الجديد فقط، ولا يعيد توليد المقالات القديمة.

إذا فشل التوليد أو انتهت الحصة أو لم يظهر manifest كامل: **توقف ولا تنشر**.

### 5. تحقق من الصوت قبل البناء الكامل

يجب أن يوجد:

`public/audio/articles/34e34b6f4633d928/manifest.json`

وتحقق من:

- `articleId` الصحيح.
- `provider` = Google Gemini API للمسار المجاني المعتمد.
- `model` و`Sadaltager` واللغة متوافقة مع نظام بريق الحالي.
- كل Parts وملفات MP3 موجودة.
- bytes وSHA-256 والمدد صالحة.
- sync IDs كاملة وغير مكررة.

واستمع يدويًا إلى المقاطع التي تحتوي ETA وe-Visa وArton Capital وPassport Index وC-181/23 والكلمات العربية المضبوطة.

### 6. شغّل البناء الكامل فقط بعد اكتمال الصوت

```bash
npm run build
```

يجب أن يمر كاملًا دون bypass أو تعطيل أي Gate.

الحالة المستهدفة بعد تطبيق الحزمة:

- 14 مقالًا منشورًا.
- `PENDING_CLOUD = 12`.
- `RETAINED_GEMINI = 2`.
- `check-audio-dist`: 14/14.
- كل بوابات V4.20/V4.21.0/V4.21.1/V4.21.2/V4.21.3/V4.21.4 خضراء.

## فحص الصفحة بعد البناء

قبل أي Merge افحص الصفحة المبنية فعليًا على 320 و390 و430 و768 و1024 و1440 و1890 بكسل، وتحقق من:

- H1 واحد.
- العنوان والتاريخ والتصنيف ومدة القراءة.
- الصورة الرئيسية والـthumbnail والـSocial Card.
- Quick Summary وTOC (H2 فقط).
- الروابط الخارجية والربط الداخلي إلى مقال القوة الناعمة.
- الوضع الداكن وحفظ المقال وأزرار المشاركة.
- تشغيل/إيقاف/استكمال الصوت والسرعة.
- تقديم شريط الصوت وانتقال النص إلى الموضع الصحيح.
- حفظ موضع الاستماع.
- عدم ظهور provider/model أو تفاصيل Parts للمستخدم.
- عدم وجود horizontal overflow أو Console errors أو روابط 404.
- canonical وsitemap وBlogPosting/Breadcrumb Schema.

## قاعدة القرار

لا Merge إلى `main` ولا نشر على Cloudflare إلا إذا:

1. تم تطبيق الملفين بالترتيب.
2. تم تحديث `publishedAt` للوقت الحقيقي.
3. وُلد صوت المقال المستهدف واختُبر يدويًا.
4. وجد manifest كامل في المسار المتوقع.
5. نجح `npm run build` كاملًا وهو `draft:false`.
6. نجحت المعاينة النهائية على الجوال وسطح المكتب.

إذا أخفق أي بند فالحالة هي:

**NOT READY TO PUBLISH**

وبعد اجتيازها كلها فقط:

**READY TO PUBLISH**
